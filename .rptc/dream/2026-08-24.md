## Proposed 1 — fix `.rptc/CLAUDE.md`: it documents the broken jest redirect order

**Finding.** The project's own instructions teach the exact mistake the `gate` skill
warns about, in the two places a session is most likely to copy from.

**Evidence.**

- `.rptc/CLAUDE.md:26` (Essential Commands) —
  `npx jest --no-coverage 2>&1 > /tmp/jest-output.txt   # Full suite`
- `.rptc/CLAUDE.md:92` (Test-Command Gotchas) — the same string again.
- `.claude/skills/gate/SKILL.md:28-30` — "**Redirect order matters.** Jest writes its
  results to STDERR. `cmd 2>&1 > file` points stderr at the terminal *first*, then
  sends stdout to the file — so the file lands EMPTY and every `grep -c FAIL` on it
  returns a clean-looking `0`. Write `> file 2>&1`."

Measured across the 6 sessions: **10 jest invocations used the wrong order, in 4 of 6
sessions** (`9b10bc8b` ×3, `4a3175b5` ×3, `7fcefe53` ×3, `dd8ea485` ×1), against 603
correct-order uses. The slip rate is low, but it recurs in most sessions — and it
recurs because the documented command is wrong. Sessions that reach for `gate` read
the warning; sessions doing an ad-hoc run copy `.rptc/CLAUDE.md` and get the broken
form. This run's own session is one of the four.

**Change.** In `.rptc/CLAUDE.md`, both lines:

```diff
-npx jest --no-coverage 2>&1 > /tmp/jest-output.txt   # Full suite (~20s, see below)
+npx jest --no-coverage > "$SCRATCH/jest-output.txt" 2>&1   # Full suite (~20s, see below)
```

**Risk if wrong.** None. `> file 2>&1` is strictly the safe form; the gate skill,
which is the authority here, already mandates it.

## Proposed 2 — extend `10-jest-pipe.rule` to block the wrong redirect order too

**Finding.** The mistake in Proposal 1 is mechanically detectable, and a hook already
exists that hard-stops its sibling. Fixing the docs alone relies on nobody writing the
command from memory; the house rule is "prove a guard by running it", not by prose.

**Evidence.** `.claude/hooks/rules/10-jest-pipe.rule` blocks
`jest … | tail|head|grep` with `rule_once=0` ("a hard stop on a mechanical mistake,
not a nudge"). It does not match `2>&1 > file`. The two failures are the same class —
both make a run's real result invisible — and only one is guarded. Note the failure
mode is strictly worse here: a piped run *looks* hung, which is obvious; a wrong-order
redirect produces a green-looking zero, which is not.

**Change.** Add to `rule_match`, or add a sibling rule `11-jest-redirect.rule`:

```sh
printf '%s' "$2" | grep -qE '(^|[[:space:]/])jest[[:space:]][^|;]*2>&1[[:space:]]*>[[:space:]]*[^&]'
```

with a message naming the correct form. Prove it by running it both ways before
committing — a rule pinned by a string match is what this repo has been bitten by.

**Risk if wrong.** A false positive on a deliberate "stdout to file, stderr to
terminal" jest run. That combination has no use here, and the match is jest-scoped.

## Proposed 3 — settle the `/tmp` contradiction; right now the guidance loses

**Finding.** Three tracked artifacts instruct the agent to write jest output to
`/tmp`, while the session-level instruction says to use the scratchpad directory and
"Only use `/tmp` if the user explicitly requests it." When instructions disagree, the
one written into a command string wins, every time.

**Evidence.**

- `.claude/hooks/rules/10-jest-pipe.rule:20` — the block message itself says
  `> /tmp/jest-output.txt 2>&1`. This is the highest-authority text in the loop: it is
  what an agent reads at the exact moment it is being corrected.
- `.rptc/CLAUDE.md:26` and `:92` — same path.
- Measured: bare `/tmp` use appears in **6 of 6 sessions**, 169 occurrences
  (`22d27ed6` alone ×109).

6-of-6 non-adherence is not an agent discipline problem. It is an instruction conflict,
and the losing side is the one with no command string attached.

**Change.** Pick one and make all four artifacts agree. Recommended: keep the
scratchpad expectation and strip `/tmp` from the rule message and both `.rptc/CLAUDE.md`
lines (folds into Proposal 1's edit). The alternative — dropping the scratchpad
expectation — is worse: the scratchpad is per-session and auto-cleaned, `/tmp` is not.

**Risk if wrong.** Low. `$SCRATCH` must be defined in the shell that runs the command;
if a session does not set it the redirect fails loudly rather than silently, which is
the correct direction for this failure.
