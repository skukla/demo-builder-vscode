## Proposed 1 [APPLIED]: add a PreToolUse hook routing webview-test edits to `webview-test-authoring`

**Finding.** `webview-test-authoring` has fired **0 times in 70,727 turns** while its trigger
occurred continuously.

**Evidence.** `attributionSkill` never contains it across all four transcripts. In session
51919d87 alone: **17 webview/UI test files touched** (`IntegrationDetailPanel.test.tsx` ×13,
`ProjectDashboardScreen-integrations.test.tsx` ×8, `IntegrationsGrid.test.tsx` ×7, …) and **10 tool
calls hand-writing a `jest.mock('@adobe/react-spectrum')` preamble**. The session also hit
`"Unable to find an accessible element with the role \"button\" and name \"Change\""` — a string the
skill's own description names as a trigger. Seen in 4/4 sessions (never fires); acute in 1.

**Root cause — and why the 2026-07-30 fix does not cover it.** That run added the
invoke-don't-transcribe convention, which only helps when something *names* the skill. Nothing names
`webview-test-authoring` at the moment you open a webview test. Its description is good and precise;
descriptions are simply not consulted unless the agent thinks to look. Routing that depends on
remembering to look is not routing.

**Change.** A `PreToolUse` hook on `Write`/`Edit` matching `tests/**/ui/**/*.test.tsx` (and
`*.testUtils.tsx`) emitting a one-line reminder to invoke the skill. Precedent exists in this repo:
`.claude/hooks/jest-pipe-guard.sh` mechanically enforces a rule that prose had failed to.

**Risk if wrong.** Low, but real: hook noise on every webview test edit. Mitigate by firing once per
session, or only when the file does not already contain a Spectrum mock preamble.

## Proposed 2 [APPLIED]: generalize the feature-scoped-CSS gotcha in `spectrum-webview-ui`

**Finding.** The skill records this trap too narrowly, and the narrow version did not transfer.

**Evidence.** Current text: *"Warning-text utilities like `text-orange-500/600` are feature-scoped
(`eds-steps.css`), NOT global — define a local class instead."* On 2026-07-31 the same trap recurred
in a different shape: `DestinationStage.tsx:103` used `.service-action-link`, defined in
`src/features/eds/ui/styles/connect-services.css`. That sheet reaches the **wizard** bundle only
because `StorefrontStep.tsx:52` imports it as a side effect. In the integrations bundle the class
does not exist, and the button rendered as a raw grey box — reported by the user as "This UI looks
broken". 2/4 sessions (the original incident + this one), different classes, same cause.

**Change.** Replace the bullet with the general rule and its mechanism:

> **A CSS class working in one webview proves nothing about another.** Each webview bundle is a
> separate esbuild entry, and feature stylesheets arrive only via side-effect `import` somewhere in
> *that* entry's graph. `.service-action-link` (EDS `connect-services.css`) styles correctly in the
> wizard solely because `StorefrontStep` imports the sheet; the same component rendered raw on the
> integrations surface. Before reusing a component across surfaces, confirm its classes are in a
> sheet the target bundle loads — or move them to `custom-spectrum.css`, which every bundle imports.

Also note `.inline-action-link` (added 2026-07-31) as the global home for small inline text-button
actions, so the next occurrence has somewhere to land.

**Risk if wrong.** None — strictly more accurate than the text it replaces.

## Proposed 3 [APPLIED — option (a)]: capture cross-surface component reuse

**Finding.** Reusing the wizard's `AddIntegrationFlowModal` on the integrations surface failed
**three times in one session, in three distinct layers**, each fix revealing the next.

**Evidence.** All in 51919d87, all user-reported:
1. **State shape** — "when I click next, the web view shows blank". `isAdobeSignedIn` reads
   `adobeAuth` + `adobeOrg`; the adapter supplied neither, so the flow walked `dest-signin` and
   mounted `AdobeAuthStep` into a webview with no wizard state.
2. **Rendered fields** — "This UI looks broken". `DestinationSummary` renders
   `state.adobeProject?.title`; the adapter passed only `{ id }`, because `deriveStageOrder` reads
   the ids as mere booleans. State was shaped for the stage *machine*, never checked against what
   the stage *renders*.
3. **Messages** — "the list-org-console-apis request timed out". Registered only in
   `ProjectCreationHandlerRegistry`; the integrations panel registers `dashboardHandlers`. An
   unregistered type is not an error, it is silence — the request never resolves.

1/4 sessions, but three independent occurrences with a shared root: **reusing a component inherits
its whole dependency graph — props, rendered fields, messages, and stylesheets — and none of those
fail loudly.**

**Partially mechanized already.** Layer 3 now has a generic guard
(`tests/features/dashboard/commands/showIntegrations-handlerCoverage.test.ts`) that scans the reused
flow's source for every `webviewClient` request/postMessage literal and fails if the host panel does
not register it. Verified red by reverting the registration. Layers 1–2 are not mechanizable the
same way.

**Change — two options, PM to pick.**
- **(a) Extend `webview-command-handler`** with a "reusing a component from another surface"
  section. Lower cost, and that skill already carries new-surface traps. Weaker routing: two of the
  three failures were not about messages at all.
- **(b) A new short skill** (`cross-surface-component-reuse`). Better routing to the actual
  situation; costs a 22nd skill and overlaps three existing ones (`webview-command-handler`,
  `wizard-step-authoring`, `spectrum-webview-ui`).

Recommendation: **(a)**. Three occurrences in one session is not yet cross-session prevalence, and
the corpus already routes reasonably. Revisit if it recurs after the integrations work ships.
