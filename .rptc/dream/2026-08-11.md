## Proposed 1 — rewrite `spectrum-webview-ui` §Verify: it asks for an eyeball the agent does not have

**Finding.** The skill's verification step is addressed to a human. Step 2 reads *"Eyeball the
actual surface"* — the agent cannot: the UI renders in a VS Code webview, unreachable by
Playwright, screenshot, or devtools. The global `CLAUDE.md` "verify in the browser after
frontend changes" rule is likewise inert here. So the step is silently skipped, visual claims
get made by reading CSS instead, and **the user is the only renderer in the loop**.

**Evidence.** Sixteen user turns carried a screenshot, in **3 of 4 sessions** (`a5db29a6` 9,
`fd870e89` 6, `68153a78` 1). Every visual defect in the window was caught by the user from one
of those, none by the agent. The recurring shape is a **parity claim that reading CSS cannot
support** — 4 instances across 3 sessions:

- `a5db29a6`: *"The integrations dashboard has more padding on the left and right… I want the
  integrations dashboard to have the same width and padding as the project dashboard."*
- `fd870e89`: *"Why is it that when an integration is deploying, its card looks like it has
  different line spacing: [Image #19]"*
- `fd870e89`: *"can we make sure the step names that appear in the wizard timeline view all have
  the same appearance? Here's a good one: [Image #23] Here's a bad one: [Image #24]"*
- `68153a78`: *"Update the status row on an integration flyout to use the all-caps styling and
  the already-used spacing between status dot and status label"*

And the sharpest case, from the session handoff: `.integration-card` carried the comment
*"Matched to `.project-card-spectrum`"*, had **identical declarations**, and rendered at a
different height. The fix that actually held was structural — shared custom properties, now at
`src/core/ui/styles/custom-spectrum.css:596-599` (`--card-min-height`, `--card-min-width`,
`--card-padding`, `--card-gap`; 14 references, verified this run against a positive control).

Two further corrections show the same root cause — designing a surface without seeing it
populated: *"Revert it and lose the entire hint thing"* (a per-row hint built for 6 interesting
rows annotated all 717) and *"There's no point in a dot in this case."*

**Change.** Replace the `## Verify` preamble and step 2 in
`.claude/skills/spectrum-webview-ui/SKILL.md`:

```markdown
## Verify

**You cannot see this UI.** It renders in a VS Code webview — no Playwright, no screenshot, no
devtools you can reach. The global CLAUDE.md "verify in the browser" rule does not apply here
and nothing automatic replaces it. The user is the only renderer, so:

- **Never report a visual result you did not see.** "The rows line up now", "this matches the
  project card" — that is a prediction. Say so, or ask for a screenshot.
- **Never assert parity from declarations.** Identical properties render differently under
  different ancestors. `.integration-card` was commented "Matched to `.project-card-spectrum`",
  had the same declarations, and rendered at a different height.
- **Make parity structural instead.** One shared custom property both surfaces consume
  (`--card-min-height` / `--card-padding` / `--card-gap`, `custom-spectrum.css`). A number that
  exists once cannot drift; a number copied twice already has.
- **Check a list's real cardinality before designing per-row anything.** A per-row hint built
  to explain 6 rows annotated all 717 and was reverted.

Then, with the user driving:
1. `npm run watch:all` in the background; F5 once, then Cmd+R in the Extension Dev Host.
2. Ask for a screenshot of the surface **populated** — an empty one hides every density,
   overflow and cardinality bug. Check: decoration centered at both scales; grouped/submenu
   Menu opens and the submenu is reachable; nothing overflows its container.
3. Open the webview devtools console — no errors; a hang or repeated identical renders points
   at an inline empty-array/object reference passed to a hook.
4. If you touched inline styles: `npx jest tests/sop/inline-styles.test.ts --no-coverage`.
```

**Why the skill and not CLAUDE.md.** It is webview-specific and the skill already routes on
every Spectrum/CSS task; the root file should not carry a per-surface verification recipe.

**Risk if wrong.** One extra screenshot request per visual change. The cost of the current
wording is a wrong visual claim reaching the user, which happened 16 times in 4 sessions.

## Proposed 3 — one line onto root `CLAUDE.md` §Verifying: quote glob arguments

**Finding.** The 2026-08-07 positive-control rule works (see Notes), but the *specific* zsh
failure it keeps catching is unnamed and recurs: an unquoted `--include=*.css` is glob-expanded
by zsh before `grep` sees it, so the search never runs and the count reads as a legitimate zero.

**Evidence.** 2 sessions. `fd870e89` — inside a positive-control block, which is what saved it:
`ugrep: warning: .rptc/research/pdp-prerender-validation …: No such file or directory` followed
by `*** CONTROL FAILED ***`. And this dream session, twice: `(eval):3: no matches found:
--include=*.css` printed `--card-* occurrences: 0`, which would have read as "the shared tokens
were never added" had the stderr not been visible.

**Change.** Append to the existing `## Verifying` section in root `CLAUDE.md`:

> **Quote glob arguments in zsh.** `--include=*.css` is expanded by the shell before `grep`
> sees it and the command dies with "no matches found" — printing a zero that looks like a
> result. Write `--include='*.css'`.

**Risk if wrong.** Two characters. None.

## Proposed 5 — ACCEPTED and applied: a control must be run at the question's scope

**Finding.** The 2026-08-07 positive-control rule is working (see Notes) but has a blind
spot it does not name: a control run at the *wrong scope* inherits the mistake and passes.
Every wrong answer this session came from a correct command aimed at the wrong tree, and the
control confirmed the tool worked while the aim was still wrong.

**Evidence.** Five instances in ONE session (`de913f93`) — enough on its own, since the
whole point is that they are indistinguishable from success at the time:

| # | The command was right; the aim was not | The wrong conclusion |
|---|---|---|
| 1 | grepped `src/features/components/config/`; catalog is in `project-creation/config/` | "`appbuilder-shell-app` is unmerged" — it had shipped |
| 2 | grepped `.claude/skills/`; the App Builder skills are GLOBAL (`~/.claude/skills/`) | "12 of 13 durable facts are in no skill" — nearly all were |
| 3 | `${PIPESTATUS[0]}` is bash; this shell is zsh (`$pipestatus`, 1-indexed) | both exit codes returned **empty**; blank output read as "tsc and eslint pass" |
| 4 | eslint control written to `/tmp` — outside the base path | "File ignored"; exit 0 proved nothing about eslint's behaviour |
| 5 | a setting name written from memory into **release notes** | `demoBuilder.eds.defaultDaLiveOrg`; the real key is `demoBuilder.daLive.defaultOrg` |

\#5 is the one that matters most: it was hours from shipping a wrong setting key to every
beta user, and it had no command behind it at all — it was recall presented as fact. Caught
only by diffing `package.json` against the `.126` tag.

**Change.** Two paragraphs appended to root `CLAUDE.md` `## Verifying` — one stating that a
control proves the tool works rather than the aim ("say where the answer would be if it
existed, then confirm your command reads there"), with the four scope failures as evidence;
one forbidding publishing an identifier not read from source.

**Why now rather than next run.** Normally one session is a note, not a finding — but the
prevalence rule exists to filter *coincidence*, and five instances of one mechanism inside
one session is not that. Waiting would also have meant leaving the release-notes near-miss
unrecorded while the memory of it was the whole evidence.

**Risk if wrong.** One extra grep before asserting a negative, and one before naming an
identifier. Against a wrong setting key reaching users, that is not a close call.
