## Proposed: add to root `CLAUDE.md` — reading is per-conversation, and grep is not reading

**Finding.** The single most common failure across the corpus is attempting to edit a
file the conversation has not Read. It is not a missing instruction — the global
CLAUDE.md already says "Always read a file before writing to it" — it is that the
rule is understood as *knowing the content* rather than *having called Read in this
conversation*.

**Evidence.**
- `File has not been read yet. Read it first before writing to it.` — **71 occurrences
  across 6 of 12 sessions**, the top tool error by a factor of three.
- `File has been modified since read, either by the user or by a linter.` — **12
  occurrences across 4 sessions**. Same root, different trigger: this repo's
  format-on-edit hook rewrites files after every edit, so a read can be invalidated
  by your own previous edit.
- Both fired in this session: twice on `tests/register-publish-key/index.test.js`
  after its contents had been displayed by `awk`, and once on a test file the
  formatter had reflowed between the read and the edit.

**Change.** Add under **Verifying** in root `CLAUDE.md`:

> **Seeing a file's contents is not the same as having Read it.** `grep`, `awk`,
> `sed` and a prior session's context all show you the text without satisfying the
> Edit precondition, and the error arrives only after you have composed the edit.
> Read the file — or the specific range — before editing anything you located with
> a shell command.
>
> **The format-on-edit hook can invalidate your own read.** It rewrites files after
> an edit (trailing commas, line wrapping), so a second edit against a region you
> read *before* the first one may no longer match. When an edit fails on a string
> you are sure is present, re-Read rather than re-deriving the string.

**Risk if wrong.** Low — it adds two paragraphs to a section that already exists and
contradicts nothing.

## Proposed: add to root `CLAUDE.md` — a comment about ANOTHER component is a claim that rots

**Finding.** A comment asserting what a different component does has no mechanism
keeping it true, and reads as verified fact to whoever finds it next. In this session
two such comments hid a live, shipped bug.

**Evidence.** `actions/register-publish-key/index.js:22` and `actions/lib/key-store.js:60`
both stated the extension "re-registers on a schedule". No schedule existed. The
claim was written the same day, by the same author, describing a sibling repo — and
it was false on arrival. Chasing it is what surfaced that **reset and rename destroyed
each site's publish key and never re-minted it**, which had already shipped and would
have gone out again in this release.

Single occurrence, but severity is high enough to record: the comment did not merely
go stale, it actively suppressed the question that would have found the defect.

**Change.** Add under **Verifying** in root `CLAUDE.md`:

> **A comment describing what ANOTHER module does is a claim, not documentation.**
> Nothing keeps it true — not the compiler, not the tests, not a scan. Before writing
> one, name the code that makes it true and cite it; if you cannot, write what you
> actually verified instead. Before RELYING on one, check it. On 2026-08-15 two
> comments asserting a re-registration schedule that never existed concealed a
> shipped bug for as long as they went unquestioned.

**Risk if wrong.** Low. The failure mode is mild over-caution about cross-module
comments, which is cheap next to what it caught.

## Notes (single occurrence — not yet actionable)

### A self-check fed the same input as the thing it checks proves nothing
The proposed verification for a corrupted key store was to write a key and read it
straight back. Both operations use the same `ENCRYPTION_KEY`, so it round-trips
cleanly precisely when every *previously* stored key has become unreadable — the one
failure it was meant to detect. The working check reads a record written by an
EARLIER deployment. Watch for a second instance before proposing a rule; the shape
("the control shares the fault it is testing for") already appears in CLAUDE.md's
scope-mismatch section and may belong there rather than as its own entry.

### Work hung off a lifecycle event whose precondition that event does not establish
The publish-key renewal sweep ran at activation and needed a DA.live session.
Measured on a real run: the extension started at 21:58:01, the stored token was
already expired at 21:58:35, and a valid one arrived at 21:58:55. Activation is the
moment the precondition is *least* likely to hold. Fixed by adding an `onDidSignIn`
trigger. One occurrence; if a second appears, it becomes a rule.

### Positive: the zsh glob-quoting guidance is working
CLAUDE.md records unquoted globs as having "recurred twice on 2026-08-11". Across the
12 sessions since, the glob hook fired **twice total**. The documentation did its job
— worth keeping as evidence that these entries pay off, and worth NOT deleting as
"old news".

### Jest hooks are absorbing what the docs did not
`1 jest run is already in flight` fired 13 times across 4 sessions; `never pipe jest
through tail/head/grep` fired 11 times across 6. Both rules are in CLAUDE.md AND
enforced by hooks. The hooks are catching what the prose does not prevent, which is
the system working as designed — no change proposed, recorded so the next run does
not read these counts as a new problem.
