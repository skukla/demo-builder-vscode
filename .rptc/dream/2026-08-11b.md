## Proposed 1 — add a causal-claim rule to root `CLAUDE.md` §Verifying

**Finding.** Every rule now in §Verifying governs claims about **facts** ("nothing found",
"this identifier exists", "the control passed"). None governs claims about **causes**. In one
session, five separate explanations for a single bug were proposed and then falsified, each by
a single cheap command that was available the whole time.

**Evidence.** First-hand, one session (2026-08-11, push-protection debugging), five instances:

| # | Cause proposed | Falsified by | Cost |
|---|---|---|---|
| 1 | A secret in `boilerplate-b2b-template` | `curl` the tarball, scan it — clean | user sent to chase Adobe's repo |
| 2 | Git Data API bypasses push protection; Contents API does not | `POST /git/trees` with the same content — also blocked | shaped a proposed fix that would have been wrong |
| 3 | It is a repository ruleset, not push protection | reproducing the block — identical message, it IS push protection | told the user "make it private won't help", wrong |
| 4 | Adobe enterprise custom patterns via EMU | `gh api users/jogosset` — no `_shortcode`, not EMU | one API call, never made |
| 5 | Per-user "Push protection for yourself" | user's own screenshot — enabled on the account where the write SUCCEEDS | asked the user to collect a fact that could not discriminate |

Each was stated to the user before the falsifying command was run. The user's
"This really does not solve the problem" and "I don't trust this" are the visible cost.

**Change.** One paragraph appended to §Verifying:

> **Before proposing a CAUSE, name the command that would falsify it — and run that first.**
> The existing rules here govern claims about facts. A claim about *why* something happened is
> different: it is cheap to state, expensive to retract, and the user cannot check it. On
> 2026-08-11 five explanations for one bug were proposed and each was killed by a single
> command that was available before it was offered — fetch the template, write one file, read
> one API field. If no command would falsify a proposed cause, say it is unfalsifiable from
> here and name who can test it, rather than presenting it as the explanation.

**Risk if wrong.** Adds friction to legitimate hypothesising. Mitigated by the escape hatch —
"unfalsifiable from here" is an allowed answer, and often the correct one.

## Proposed 2 — extend the existing zsh line to cover bash array syntax

**Finding.** §Verifying already warns that `${PIPESTATUS[0]}` is bash and this shell is zsh.
The same class recurred with a different construct: `${!NAMES[@]}` (bash array-keys
expansion) failed with `bad substitution`, mid-experiment.

**Evidence.** 1 occurrence, 1 session (this one). The existing `$PIPESTATUS` note is the same
root cause, so this is a **recurrence of a covered class with an uncovered instance**, not a
new finding.

**Change.** Amend the existing sentence rather than adding a rule:

> `${PIPESTATUS[0]}` is bash and this shell is zsh (`$pipestatus`, 1-indexed) — as is
> `${!arr[@]}`, `declare -A`, and `local -n`. When a snippet uses bash array syntax, run it
> through `bash -c` or rewrite it; zsh fails these with `bad substitution`, which reads like a
> quoting typo rather than a shell mismatch.

**Risk if wrong.** None — it is additive and specific.
