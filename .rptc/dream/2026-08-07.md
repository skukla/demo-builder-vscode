## Proposed 1 — add to root `CLAUDE.md`: a verification must be able to fail

**Finding.** Piping a check into `head`/`tail`/`wc`/`grep` discards the exit code of the
thing being checked, so a `||` fallback reports success no matter what happened. Twice
this session that produced a confident, wrong "all clear".

**Evidence.** 113 commands matching `| head|tail|wc|grep … ||` across **2/2 sessions**
(101 in `fd870e89`, 12 in `51919d87`). Two false conclusions in `fd870e89`:

- Verifying colleague identifiers were removed printed `0 remaining` ten times. A zsh
  glob error meant `grep` never ran; the `|| echo` fired on a *failed command*, not an
  empty result. Caught only by adding a positive control (`RepoSelectionInline` → 26 hits).
- Checking three skills for existing coverage printed nothing for all three. `grep -c … |
  head` returns head's exit status, so `|| echo "NOT covered"` never fired. Caught by
  re-running with a known-present term per skill.

**Change.** Under a new `### Verifying` heading in root `CLAUDE.md`:

> A check whose exit code passes through `head`/`tail`/`wc`/`grep` is not a check — those
> exit 0 on empty input, so `|| echo "none"` prints "none" whether the command found
> nothing or never ran. Capture the count into a variable, or assert on it, and pair any
> "nothing found" verification with a **positive control**: the same command against
> something you know is there. Two wrong all-clears in one session (2026-08-07) were both
> caught by the control and neither by reading the output.

**Why CLAUDE.md and not a skill.** Skills load on invocation. This mistake happens in
ordinary Bash, at moments when no skill is loaded — the instruction has to be resident.

**Risk if wrong.** A few more characters per verification command. No behavioural risk.

## Proposed 2 — add to `tests/README.md`: control the test, not just the code

**Finding.** Tests that cannot fail are shipping and surviving refactors. Nothing in the
corpus warns about them.

**Evidence.** Two distinct instances, and the pattern is **older than one session**:

- `tests/features/eds/handlers/storefrontSetupHandlers-githubAppCheck.test.ts` (first
  committed **2026-03-24**, 3 commits since) defines the values it asserts on inside the
  test — `const shouldCheckGitHubApp = useExistingRepo;` — so it tests no production code.
  It passed unchanged through a 2026-08-07 change that RELOCATED the behaviour it names.
- A rollback test written this session asserted `rolledBack === true` and `moved === []`.
  Both are satisfied by doing nothing, so it passed against a deliberately disabled
  rollback. Found only by running the control.

**Change.** In `tests/README.md`, beside the existing guidance:

> **A test that passes against the disabled feature tests nothing.** After writing a test
> for new behaviour, neuter the behaviour — return early, flip the condition — and confirm
> the test fails. Assert the *observable act* (the call happened, in this order), not just
> a result flag: flags like `success:false` or an empty list are often satisfied by the
> code doing nothing at all.

**Risk if wrong.** One extra run per new test. Cheap relative to a test that never fails.
