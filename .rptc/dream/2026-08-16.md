## Proposed 2 — REORDER `appbuilder-api-subscription` so its reuse instruction fires

**Target: `~/.claude/skills/appbuilder-api-subscription/SKILL.md` — a GLOBAL skill, not a
project one.** Accepting this changes it for every project on this machine. Verified: line
45 of 49, i.e. the closing paragraph. (My first draft of this item named the project path
`.claude/skills/…`, which does not exist — caught by a control, and an instance of the very
habit Proposed 4 is about.)

**Finding.** The skill's most load-bearing instruction — call the extension's existing
wrappers instead of the raw SDK — is its final paragraph, and was read too late to prevent
the error it exists to prevent.

**Evidence.** This session. The skill was loaded deliberately, then a probe script was
hand-written against `@adobe/aio-lib-console`:

```js

```

The SDK takes **five positional arguments**. The result was
`400 Bad Request … "Unknown Error"`, which was then reasoned about as an *org restriction*

> **In-extension equivalents:** … the credential methods on `adobeEntityFetcher`
> (`getServicesForOrg`, `createAdobeIdCredential`, `subscribe*IntegrationToServices`,
> `ensureOAuthCredentialId`). **Reuse these rather than re-deriving the SDK calls.**

`adobeEntityFetcher.createWorkspaceCredential` has the correct arity and is typed; using it

**Prevalence: 1 session — a NOTE by the skill's own rule.** Proposed anyway because the fix

read top-down and acted on before the end) is general rather than specific to this skill.

> the platform-axis gotcha below, and they cannot get the SDK's argument order wrong.

## Proposed 3 — TRIM the read-before-edit paragraph in `CLAUDE.md`; it is not working

**Finding.** The guidance added by the 2026-08-15 dream run did not reduce the error. Per
session, the rate roughly tripled.

**Evidence.**

| | `File has not been read yet` | `modified since read` |
|---|---|---|
| 2026-08-15 run measured | 71 across **6 of 12** sessions | 12 across 4 |
| This window (2 days, 7 sessions) | **85 across 6 of 7** | **19 across 6** |

The 2026-08-15 proposal was accepted and is now the *"Seeing a file's contents is not the
same as having Read it"* paragraph in `CLAUDE.md`. One day later the per-session rate is
higher, not lower.

**Change.** Keep one sentence, drop the ~8 lines of incident detail:

> `grep`/`awk`/`sed`/`git show` do not satisfy Edit's precondition — Read the file (or the
> range) before editing anything you located with a shell command. The format-on-edit hook
> can also invalidate your own read; re-Read rather than re-deriving the string.

**Why not a hook.** The harness already errors on exactly this — the 85 occurrences *are*
the enforcement firing. A hook would duplicate it. And the failure is loud and
self-correcting: a wasted round trip, never a wrong answer. It is friction, not a defect.

**Why trim rather than delete.** The one-sentence form still routes a reader who hits the
error. What is not earning its place is the incident detail, which costs context in every
session and has now had two days to change behaviour and has not.

**Risk if wrong.** If the paragraph was suppressing a worse rate, trimming loses that. Not
measurable either way; the observed direction is the only evidence available.

## Proposed 4 — ADD today's instance to the falsify-first rule in `CLAUDE.md`

**Finding.** The rule *"Before proposing a CAUSE, name the command that would falsify it —
and run that first"* was violated twice in one session, both times on a signal that looked
self-evidently conclusive.

**Evidence.** This session:
1. `ACCS-REST-API … enabled: false` in an org's service catalog was read as "the org has no
   entitlement" and nearly written up as the finding. The falsifying check — read the same
   catalog in the *other* org — took one command and showed 12 other services offering
   products, which is what made the claim safe.
2. `400 … "Unknown Error"` was attributed to an org restriction across two further tool
   calls. The falsifying check was reading the caller being mirrored.

The rule's existing examples are all *shell-scope* mistakes (wrong directory, wrong shell,
unquoted glob). Neither of today's was: both were **a field in an API response that reads
like an answer**. That shape is not represented, which is a plausible reason the rule did
not fire.

**Prevalence.** 2 instances, 1 session — but the same *class* is already documented from
2026-08-11 with five instances, so this is a recurrence of a known pattern in a new shape.

**Change.** Append one line to the existing paragraph:

> A named field in an API response — `enabled: false`, a 400 titled "Unknown Error" — is a
> LEAD, not a finding. Two on 2026-08-16: `enabled:false` read as "no entitlement" (the
> other org's catalog falsified it in one call) and a 400 read as an org restriction (it was
> a malformed call, found by reading the caller being mirrored).

**Risk if wrong.** Adds three lines to a section already under scrutiny in Proposed 3. If
both are accepted the section is still net shorter.
