## Proposed 1 — ADD a rule about casts at dispatch boundaries (`CLAUDE.md`)

**Finding.** `as never` silenced the compiler at four call sites of one function,
and each produced a shipped defect that no test could see.

**Evidence.**
- `a4e0a736` (2026-08-13) — `importHandlers` read `stack?.backend`, a shape only
  wizard state has, so **every real project** resolved to `''`. Its own comment
  records it: *"The unit fixtures had the same invented shape and so agreed with
  it — a live dry run is what caught it, which no test here could have."*
- `eab4d9ed` (2026-08-17) — `edsResetUI` passed a raw `Project` through
  `as never`; `stackBackend` was undefined, so reset **never offered sample-data
  removal to anyone**.
- `9c842e16` (2026-08-17) — `sampleDataInstallDeps` did the same; the removal
  could not resolve credentials, and project creation's install was affected too.
- `ced64268` (2026-08-17) — `client as never` handed the poller a WRITE client
  with no `getJobStatus`; every poll threw.

**Prevalence.** 4 instances across 2 dates (2026-08-13, 2026-08-17), all in one
feature, all found by using the product rather than by the suite.

**Change.** Add to the Verifying section:

> **A cast at a call boundary is a silenced type error.** `as never` / `as any` on
> an ARGUMENT tells the compiler to stop checking the one thing it is good at.
> Four times in this repo it hid a field the callee dispatches on — `stackBackend`,
> which is mapped from `componentSelections.backend` and is not persisted — and
> each time the result was a silent no-op in production that every test agreed
> with. If a cast is needed to pass something, the shape is wrong: build the object
> the callee declares, and let it fail at compile time.

**Risk if wrong.** Casts are sometimes load-bearing (an `unknown` interface
boundary). The rule says "at a call boundary", not "never", which leaves those.

## Proposed 2 — ADD the mock-hides-the-call trap to `webview-test-authoring` §8

**Finding.** All four defects above survived because the collaborator was mocked,
and a mock answers correctly regardless of what it is handed.

**Evidence.** Every suite touching credential resolution mocks
`resolveCommerceCredentials`. The mock returns `{ok:true}` whatever object it
receives, so a project missing the dispatch field is indistinguishable from a
correct one. Twelve existing tests stayed green across all four defects. The fix
that finally caught it asserts **the argument**, not the outcome:
`expect(mockedCredentials).toHaveBeenCalledWith(expect.objectContaining({project:
expect.objectContaining({stackBackend: 'adobe-commerce-accs'})}))`.

**Prevalence.** 4 instances, 2 dates — same set as Proposed 1, different lesson:
that one is about the cast, this is about why the suite could not help.

**Change.** Add to §8 ("Changing a contract means auditing its MOCKS"):

> **The inverse also bites: a mock cannot see a malformed CALL.** It answers the
> same whatever it is handed, so a caller passing a wrong-shaped argument looks
> identical to a correct one. When the thing under test is *how a collaborator is
> invoked* — a dispatch field, a scoped id, which client is passed — assert the
> ARGUMENT, or drive the real collaborator with `jest.requireActual`. Asserting
> the outcome tests the mock.

**Risk if wrong.** Encourages argument-assertions, which are brittle if
over-applied. Scoped to "when the thing under test is how a collaborator is
invoked", which is narrow.

## Proposed 3 — SHARPEN `spectrum-webview-ui`'s read-the-DOM rule for the case where I cannot

**Finding.** The skill says *"When a style override does not take, READ THE DOM
before writing a second one."* In a webview I cannot read the DOM at all, so the
rule has no reachable action and I wrote a second, third and fourth guess instead.

**Evidence.** One CSS placement took four attempts — `right: 0` (landed ~600px
away, because the field is `flex:1 1 0`), then beside the label text, then
centred in the field, then a shrink-to-fit wrapper — each shipped and each
reported as a prediction. By contrast, when a *different* CSS question came up
minutes later I asked for the location first, got a screenshot, and fixed it in
one commit (`b990588d`, the double divider).

**Prevalence.** 1 session, 4 attempts on one element, with a same-session control
showing the alternative works. Marked as a **note-strength** finding by the
skill's own bar (single occurrence) — but the control is what makes it worth
proposing anyway.

**Change.** Amend the existing bullet:

> **When a style override does not take, READ THE DOM before writing a second
> one.** In this webview you cannot — so the second attempt is not yours to make:
> ask for a screenshot of the specific element or for the DOM around it. Four
> guesses at one spinner's placement (2026-08-17) cost four build-reload cycles;
> the next CSS question that session was asked instead and took one.

**Risk if wrong.** More questions to the user. The skill already establishes the
user as the only renderer, so this follows its own logic rather than adding a new
obligation.
