## Accepted: sharpen `gate`'s description + add an invoke-don't-transcribe convention

**Finding.** An entire feature (the integrations-grid cutover: 6 new modules, 4 deletions,
3 test-file splits) was delivered without the `gate` skill ever firing. `attributionSkill`
was absent from every turn in the session.

**Evidence.** `attributionSkill` empty across all 51 assistant turns in
`51919d87-b722-43de-be0f-b1fe6dca1d4a.jsonl`. Not a discoverability failure:
`.claude/skills` is tracked (26 files), so the worktree had `gate`; and the plan named it
twice — `.rptc/plans/integrations-grid/overview.md:150` ("**Gate + visual pass**: `gate`
scoped to…") and `:180` ("full `gate` before commit"). Seen in 1/1 sessions, but with a
measurable consequence rather than mere prevalence.

**Root cause.** A backticked `` `gate` `` in prose reads as a shell command, so its three
steps were reproduced by hand. That skipped the skill body's §6 ("widen to match CI — the
scoped gate is NOT enough"): a scoped `eslint` ran first and reported clean, and only a
later whole-repo run surfaced 28 errors. The skill's content was correct and would have
prevented this; it was simply never loaded.

**Change.**
1. `.claude/skills/gate/SKILL.md` front matter — description now says to INVOKE rather than
   re-run by hand, names the §6 consequence, and adds the trigger "whenever a plan step or
   doc says to run the gate". The description is the only text read before invocation, so
   it is the only place this instruction has leverage.
2. Root `CLAUDE.md`, Project Skills section — added the general convention: a backticked
   skill name is an instruction to invoke, not a command to reproduce.

**Risk if wrong.** Low. Both edits are additive prose in files already loaded every session;
neither changes what the gate does.
