# Step 03 — The integration repository

A public repository built from `adobe/commerce-integration-starter-kit` v4 (App Management
generation; node 24; `app.commerce.config.ts` declares providers, events, registrations,
webhooks). Consumes `ERP_BASE_URL` (envSchema, providedBy the ERP entry). Calls the ERP
with an IMS token minted from the injected S2S credential (decision 12).

## What it declares (app.commerce.config.ts)

- **Webhooks** (Nishant Kapoor's design, generalised): `observer.sales_order_place_before` → `POST
  /orders` on the ERP, writes the ERP number to `ext_order_id`; the two totals-collector
  webhooks (item prices from contract pricing; the max-discount ceiling). All `required:
  false`, one-second soft timeout: when the ERP is offline, Commerce keeps its own prices
  and the order places without an ERP number (the outage demo, decision 6).
- **Events, Commerce → ERP**: company created/updated → business partner upsert
  (decision 5); product/stock created/updated → material upsert (keeps the mirror fresh
  between resets).
- **Admin UI SDK screen** (decision 9): `adminUi.menu` in `app.commerce.config` (extension
  point `commerce/backend-ui/2`, generated by the lib), opening the app's own page: health
  of both apps, the ERP link, sync log, Reset ERP records, ERP offline switch.
- **Order statuses**: a status label must exist in Commerce and belong to a state before it
  can be set, and Commerce creates custom statuses in the Admin (Stores → Order Status),
  not through REST. The integration uses statuses the instance has (`processing` +
  comment for confirmed) unless the SC adds `erp_confirmed`; the how-to says so.

## Actions beyond the kit's scaffolding

- `erp-client`: IMS-auth calls to the ERP; `/health` gate.
- `outbox-drain`: scheduled (alarm) and on-demand; drains the ERP outbox into Commerce: price
  → product price, stock → source item, partner credit/block → company credit limit/status,
  each company write recorded in the **ledger** (`lib-state`: what, before, after). Order
  status maps to THREE Commerce operations, read from the kit's code 2026-09-14: `confirmed`
  → the kit's `order/external/updated` (which is `POST /orders/{id}/comments`: a status
  history line with a status label, not a lifecycle move); `shipped` → the kit's
  `shipment-created` (`POST /order/{id}/ship`, a real shipment, the order completes);
  `invoiced` → an action we write (`POST /order/{id}/invoice`), since the kit has none.
- `reset`: decision 8 and 11 — revert ledgered company writes → ERP `/admin/wipe` → read
  Commerce products (paged) and companies → ERP bulk imports → stamp. Idempotent; reports
  counts.
- `mirror`: the import half of reset alone (first install runs it).
- `set-offline`: `PUT /settings` on the ERP.

## Install

App Management install as the spine drives it today (associate, reconcile). The first
successful install triggers `mirror` so the ERP has records before the first demo.

## Tests first

`lib/` under the kit's test setup: ERP client auth header and 503 handling; outbox drain
mapping per kind; ledger record/revert round-trip; reset order of operations (revert before
wipe before import) with a fake ERP and a fake Commerce; webhook responses when the ERP is
offline (no `add`/`replace`, no error).

## Done when

Deployed to a scratch workspace with the ERP from step 02: install green, an order placed
on Bodea gets an ERP number, a status change in the ERP reaches the order, a price edit
reaches the product, reset leaves the ERP mirrored and the ledger empty.
