# Step 03 — The integration repository

A public repository built from `adobe/commerce-integration-starter-kit` v4 (App Management
generation; node 24; `app.commerce.config.ts` declares providers, events, registrations,
webhooks). Consumes `ERP_BASE_URL` (envSchema, providedBy the ERP entry). Calls the ERP
with an IMS token minted from the injected S2S credential (decision 12).

## What it declares (app.commerce.config.ts)

- **Webhooks** (Nishant Kapoor's design, generalised): `observer.sales_order_place_before` → `POST
  /orders` on the ERP, writes the ERP number to `ext_order_id`; the two totals-collector
  webhooks (item prices from contract pricing; the max-discount ceiling). All `required:
  false`, one-second soft timeout: when the ERP is unavailable, Commerce keeps its own prices
  and the order places without an ERP number (robustness, not a demo scene: decision 19).
- **Events, Commerce → ERP**: company created/updated → business partner upsert
  (decision 5); product/stock created/updated → material upsert (keeps the mirror fresh
  between resets).
- **Admin UI SDK screen** (decision 9): `adminUi.menu` in `app.commerce.config` (extension
  point `commerce/backend-ui/2`, generated by the lib), opening the app's own page: health
  of both apps, the ERP link, sync log, Reset ERP records (the ERP-unavailable switch stays a test control here, decision 19).
- **Order statuses**: a status label must exist in Commerce and belong to a state before it
  can be set, and Commerce creates custom statuses in the Admin (Stores → Order Status),
  not through REST. The integration uses statuses the instance has (`processing` +
  comment for confirmed) unless the SC adds `erp_confirmed`; the how-to says so.

## Actions beyond the kit's scaffolding

- `erp-client`: IMS-auth calls to the ERP; `/health` gate.
- `outbox-drain`: scheduled (alarm) and on-demand; drains the ERP outbox into Commerce: price
  → product price, stock → source item, partner credit/block → company credit limit/status,
  each company write recorded in the **ledger** (`lib-state`: what, before, after). Order
  status maps to THREE Commerce operations, read from the kit's code 2026-09-14: `confirmed`
  → the kit's `order/external/updated` (which is `POST /orders/{id}/comments`: a status
  history line with a status label, not a lifecycle move); `shipped` → the kit's
  `shipment-created` (`POST /order/{id}/ship`, a real shipment, the order completes);
  `invoiced` → an action we write (`POST /order/{id}/invoice`), since the kit has none.
- `reset`: decision 8 and 11 — revert ledgered company writes → ERP `/admin/wipe` → read
  Commerce products (paged) and companies → ERP bulk imports → stamp. Idempotent; reports
  counts.
- `mirror`: the import half of reset alone (first install runs it).
- `set-offline`: `PUT /settings` on the ERP.

## Install

App Management install as the spine drives it today (associate, reconcile). The first
successful install triggers `mirror` so the ERP has records before the first demo.

## Tests first

`lib/` under the kit's test setup: ERP client auth header and 503 handling; outbox drain
mapping per kind; ledger record/revert round-trip; reset order of operations (revert before
wipe before import) with a fake ERP and a fake Commerce; webhook responses when the ERP is
offline (no `add`/`replace`, no error).

## Done when

Deployed to a scratch workspace with the ERP from step 02: install green, an order placed
on Bodea gets an ERP number, a status change in the ERP reaches the order, a price edit
reaches the product, reset leaves the ERP mirrored and the ledger empty.

**As built, in the plan's terms**

- Webhooks (all `required: false`, `requireAdobeAuth: true` as the kit does; Bodea, a
  Cloud Service instance, lists all three hooks in `/V1/webhooks/supportedList`):
  `observer.sales_order_place_before` → `POST orders` on the ERP → `replace
  data/order/ext_order_id` (the path root Nishant Kapoor's four lost orders established);
  totals-collector `item_prices` → ERP quote → `replace result/price_updates` with
  `{item_id, base_price}`; totals-collector `execute` → ceiling clawback as a negative
  `base_discount` on `result`. Buyer hints sent to the ERP: customer group, email,
  customer id; the ERP resolves the partner by id → Commerce company → email domain →
  customer group → default (email domain added to the ERP today: Bodea's companies mostly
  share customer group 1, so the group alone cannot tell them apart).
- ERP → Commerce is a pull: `erp/drain` every minute (alarm feed `minutes: 1`; the param
  name is `minutes`, `minute` is rejected at deploy) and on demand. Kinds: `material.price`
  → `PUT products/{sku}`; `material.stock` → `POST inventory/source-items`;
  `partner.creditLimit` → `PUT companyCredits/{id}` (ledgered); `partner.blocked` → `PUT
  company/{id}` status 3/1 (ledgered); `order.status` confirmed → comment, shipped →
  `POST order/{id}/ship` of every open line, invoiced → `POST order/{id}/invoice` +
  comment, cancelled → `POST orders/{id}/cancel`.
- Ledger in App Builder State (one key, one-year TTL, the max); reset = revert → wipe →
  mirror; a failed revert keeps only the failed entries.
- Mirror reads `products` (enabled), `inventory/source-items` (summed per SKU), `company`
  + `companyCredits/company/{id}` (404 → no B2B → no partners) and posts one import.
- Company events from Commerce are NOT subscribed (no verified event name); the mirror,
  reset and the Admin page's "Mirror" button keep partners fresh. Product deletes are not
  mirrored (the ERP has no delete route); a reset clears them.

**Live, on a scratch workspace with the ERP beside it (ErpSpikeq3e9; still deployed for
the install test):** status reaches the ERP with the injected S2S token alone (no shared
secret, decision 12 proven); a seeded material + partner give: item-prices → contract price

below the 30% ceiling, "success" within it; order-create → `ext_order_id 0000001001` with

**Facts the build taught (each cost a deploy)**

1. The lib-app's postinstall validator refuses `-` in a menu id (use `erp_integration`)
   and `;` or apostrophes in event descriptions.
2. The CLI writes no `web-src/src/config.json` (action URL map) for an extension-layout
   app. The Admin page derives its action URLs from `window.location.origin` +
   `/api/v1/web/erp/…`; safe because Demo Builder renames runtime packages only for plain
   apps (`appConfigPackages.ts`), never for extension apps.
3. When `web-src` pre-exists, the lib-app hook skips `prepareWebSourcePackage`, so
   `@parcel/resolver-default.packageExports` and `@parcel/bundler-default.manualSharedBundles`
   must be in package.json by hand or `#app.commerce.config` does not resolve.
4. **The Admin page deployed blank** ("jsxDEV is not a function"): `aio app deploy` (11.1.2
   here, 14.8.2 latest, same code) never passes Parcel a `mode`, so JSX compiles with the
   development runtime, while the lib-app hook pins `NODE_ENV=production` into `.env`, which
   Parcel inlines, so React resolves its production runtime, which has no `jsxDEV`.
   `--web-optimize`, NODE_ENV in the process env and clearing the cache change nothing.
   Fix: a `build-static` hook in `commerce-backend-ui-2/ext.config.yaml` running Parcel in
   production mode against a named browser target (the kit's `engines.node` otherwise
   makes Parcel infer a Node target and externalise every dependency: a 6 KB bundle).
   Demo Builder's deploy needs no flag. Standalone the page now renders (its "No sign-in"
   notice, as designed outside a host). Memory: `reference_admin_ui_sdk_page_blank_jsxdev`.
5. Inside the Experience Cloud shell the page stayed dark (the shell's frame never
   completed its handshake; the ExC route is the lib-admin-ui's fallback host, the Commerce
   Admin is the real one). Verify inside the Commerce Admin after the install; if the shell
   matters, compare with the lib-app template, which ships no `exc-runtime.js` loader.
6. The App Builder CDN caches `index.html` for minutes after a deploy (`x-cache: Hit`,
   age 278 s), so a redeployed page can show the previous bundle for a while.

**Correction (owner, 2026-09-14): Commerce is the master the SC prepares in; the ERP adapts.**
The first cut let the ERP keep its list price, stock, credit limit and block once a record
existed, which would have let a product re-priced in Commerce during preparation keep an
old ERP price. Changed on both sides: the ERP's import now takes every field Commerce sends
(fields it omits keep their ERP value); the integration re-subscribes the kit's stock event
(`observer.cataloginventory_stock_item_save_commit_after`, SKU looked up by product id),
refreshes the business partners from Commerce on every drain (companies, credit, blocked),
and the mirror carries `blocked` from company status 3. An ERP-side edit still reaches
Commerce through the outbox and comes back on the next import as the same value, so the
two never fight.

**Rebuilt (owner, 2026-09-14, decision 20): the ERP publishes events; no pull.** Gone:
`erp/drain`, `src/lib/drain.js`, the outbox routes. Restored from the kit and extended: the
ingestion webhook (`require-adobe-auth: true`; the ERP calls it with its own IMS token),
the external provider `erp` with eight `be-observer.*` events, and the handlers
`product-backoffice/updated` (sparse product save: name, price), `stock-backoffice/updated`
(the kit's), `order-backoffice/updated` (status comment), `order-backoffice/shipment-created`
(ships the lines the ERP names by Commerce item id, which the order-create webhook now sends
to the ERP), `order-backoffice/invoice-created`, `order-backoffice/cancelled`,
`company-backoffice/credit-updated` and `company-backoffice/status-updated` (both ledgered).
What stays scheduled: `erp/refresh-partners` every minute, because Commerce raises no event
for companies. The ERP side: `lib/events.js` journals each change, delivers it to
`https://<namespace>.adobeio-static.net/api/v1/web/ingestion/webhook` at once, and an alarm
retries pending ones every minute; its screen shows the event log.

Consequence for proving it: `publishEvent` in the ingestion webhook resolves provider and
event ids from data the App Management install writes, so the ERP → Commerce direction can
only be proven after the install into a Commerce instance.

**Owner review, 2026-09-14 (later):** three more changes.
1. **Products, not materials.** The owner asked whether the record should not just be
   products or SKUs; SAP's word stayed only in the plan's history. Renamed across the ERP
   (collection, route, screen page, tests) and in what the integration sends.
2. **Retry cap.** An ERP event Commerce refuses for good (shipping an already shipped order)
   would otherwise retry every minute forever. After ten attempts an event is marked failed,
   leaves the queue, shows as failed on the ERP's Events page, and can be requeued there.
3. **The contract, and the pin against drift.** `contract/erp-contract.json` in the ERP
   states its routes, its import/quote/order shapes, every event with its payload keys, and
   the delivery rules; `test/contract.test.js` raises every event against an in-memory
   database and compares the payload keys to it. The integration vendors the file
   (`contract/erp-contract.json`) and `test/contract/erp-contract.test.js` fails when a
   subscribed event is not raised, a handler schema asks for a key the ERP does not send, or
   a called route does not exist; `npm run contract:check` fetches the ERP's main and says
   when the vendored copy is behind. Both READMEs now carry an "APIs and events" section
   listing every Commerce webhook, event and REST call and every ERP route and event.

Still open from the owner's questions: `ext_order_id` is a native order field, written by
the before-webhook and read back through REST, but not shown in the Commerce Admin order view
by default; an Admin UI SDK order-grid column from this app is the natural way to show it.
Orders placed before a reset live on in Commerce only; the ERP's Sales orders page should say
so (step 06 acceptance item).

**Also (2026-09-14, later):** Commerce's `soft_timeout` only logs (webhooks XML schema page:
"Requests exceeding this timeout are logged for debugging purposes"); the hard `timeout`
aborts. The two totals-collector hooks now carry `timeout: 5000` with the ERP call budgeted
at 3 s, so a cold ERP action (the first cart total after a quiet spell) still answers; the
earlier 900 ms budget made the first total fall back to Commerce's price. `erp/detach` and
the order-number clearing in reset are decision 21; the ERP's `GET orders` is what tells the
integration which orders to clear.
