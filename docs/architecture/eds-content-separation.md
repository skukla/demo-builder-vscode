# EDS content separation

An EDS storefront is two repositories that do not know about each other, plus a file
that joins them.

| | Holds | Edited by |
|---|---|---|
| **GitHub repo** | code — blocks, scripts, styles | developers |
| **DA.live** | content — the pages | authors |

Neither contains the other. That is the point of the architecture: an author changing
a page never touches the code repo, and a developer shipping a block never touches
content.

## `fstab.yaml` is the join

It lives in the code repo and points at the content source. Helix reads it to know
where a site's content comes from, so it is the one file that must be right for a
storefront to render at all.

Generated by `services/fstabGenerator.ts` — `generateFstabContent` is the single
source of truth. Do not hand-assemble the YAML anywhere else; a storefront with a
subtly wrong mount point fails in a way that looks like a publish problem.

## Spreadsheets cannot be created programmatically

EDS uses spreadsheets for configuration — placeholders, redirects, metadata. They are
`.xlsx` in DA.live and served as `.json` by the CDN
(`/placeholders/global.xlsx` → `…/placeholders/global.json`).

**DA.live's `/source/` API has no spreadsheet handling.** Everything below was tried
and none of it works:

| Tried | Result |
|---|---|
| HTML table as `.html` | creates an HTML document, not a spreadsheet |
| HTML table, no extension | 404 |
| JSON directly | 404 — not served as an endpoint |
| `.xlsx` binary | stored as a raw file |
| `.xlsx` with `helix-` prefixed sheets | same — raw file |

Root cause verified two ways: DA.live's API documentation describes only generic
blob upload via `multipart/form-data`, and `da-admin`'s `put.js` treats all data
generically with no content-type inspection.

**So a spreadsheet must be created in the DA.live UI**, and anything automated has to
copy an existing one rather than construct it. A feature that needs a new spreadsheet
needs a human step; designing around that is cheaper than rediscovering it.
