# EDS content separation

An EDS storefront is two repositories that do not know about each other, plus a file
that joins them.

| | Holds | Edited by |
|---|---|---|
| **GitHub repo** | code — blocks, scripts, styles | developers |
| **DA.live** | content — the pages | authors |

Neither contains the other. That is the point of the architecture: an author changing
a page never touches the code repo, and a developer shipping a block never touches
content.

## `fstab.yaml` is the join

It lives in the code repo and points at the content source. Helix reads it to know
where a site's content comes from, so it is the one file that must be right for a
storefront to render at all.

Generated by `services/fstabGenerator.ts` — `generateFstabContent` is the single
source of truth. Do not hand-assemble the YAML anywhere else; a storefront with a
subtly wrong mount point fails in a way that looks like a publish problem.

## A spreadsheet is written as DA.live's own JSON document

EDS uses spreadsheets for configuration — placeholders, redirects, metadata. The CDN
serves each one as `.json` (`…/placeholders/cart.json`).

**A sheet is created by POSTing DA.live's native sheet document to
`/source/{org}/{site}/{path}.json`, then previewing and publishing that `.json` path.**
`buildSheetDocument` in `services/daLive/daLiveSpreadsheetUtils.ts` is the one place
that knows the document's shape. Two writers use it: the block library's sheet
(`DaLiveBlockLibrarySheet.createJsonSpreadsheet`) and the content copy
(`copySpreadsheetFile`, which reads the source sheet off the public CDN and keeps
every sheet in it).

The whole-site publish does not publish sheets. A copied sheet is published by path,
from the list the copy reports (`sheetPaths`), by the pipeline's `sheet-publish` step.

What was measured, 2026-10-12, on a scratch storefront (EDS-40):

| Written | Result |
|---|---|
| The native document at `/.da/library/blocks.json`, previewed and published | a real sheet: 200, with and without `?sheet=data` |
| HTML table as `.html` | an HTML page; `<path>.json` answers 404 |

Measured the same day on a reset of a project copied from a colleague's demo
(`.rptc/research/added-demo-content-completeness/research.md`, section 9): a native
document OUTSIDE `/.da/` is served too. `/metadata.json` and `/redirects.json` went from
404 to 200 with the source's rows.

**A file in the repository at the same path wins over the sheet.** The 16 label sheets
(`/placeholders/<area>.json`) were written and published, and the site went on serving
Demo Builder's one-row stub file for each. With the stub deleted from the repository and
the sheet published once more, the site served the source's rows (cart: 160). So a
label-sheet stub is written only for an area the content source serves no sheet for:
`placeholderStubPathsFor` in `services/placeholderStubs.ts` asks the source, and creation
and reset both take their list from it.

Earlier attempts, recorded before the native document was understood. The table said
"JSON directly: 404" without recording which JSON shape was sent or whether the path
was published, so it does not contradict the row above:

| Tried | Result |
|---|---|
| HTML table, no extension | 404 |
| `.xlsx` binary | stored as a raw file |
| `.xlsx` with `helix-` prefixed sheets | same — raw file |
